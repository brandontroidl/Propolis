# IP Blocklist

Attacker IPs observed against a live honeypot, scored and published in nine formats.

Generated by an automated honeypot and threat-intelligence pipeline.

Check `manifest.json`'s `build_time` for when these files were actually produced, and each file's
own `valid_until` header for when its contents expire. Do not infer freshness from the commit date.

## Layout

```
tiers/        aggressive.*  standard.*        block this now
retention/    all-24h.* … all-90d.*          active in the last N
manifest.json                                 build time, counts, digests, validity
```

`tiers/` holds the two curated block-now lists; `retention/` holds the windowed
"active-in-the-last-N" lists. `manifest.json` at the root indexes every feed by name.

## What makes an entry

Every IP under `tiers/` did all four of these:

1. **Connected to a honeypot service** and completed an authenticated session - not a port
   scan, not a bare TCP connect.
2. **Did it more than once**, each time over a completed TCP connection. Single-event IPs are
   excluded, and UDP traffic (whose source address can be forged) never counts.
3. **Earned a tier recently**: its score crossed the tier's floor after activity over a completed
   TCP connection, within the time that tier is carried (see below).
4. **Was approved by a human.** No IP reaches `tiers/` automatically. An operator reviews the
   captured session - the commands run, the credentials tried, the files uploaded - and
   approves or rejects it individually.

That last point is the main thing separating this from an automated feed. It is also why the
list is small. It is meant to be high-confidence, not comprehensive.

`retention/` carries those same addresses for longer, and can also carry **volume listings**:
addresses that completed a thousand or more TCP connections to the honeypot, whether or not any
of them authenticated. A volume listing has no tier and is never under `tiers/`. By default the
operator approves each one before it is published. The software also lets an operator publish
volume listings automatically, with no review, and nothing in these files says which was done.
So treat an address that is in `retention/` and not in `tiers/` as a high-volume source, not as
a reviewed attacker. If you need every entry to rest on an authenticated session and a human
decision, use `tiers/`.

## Tiers

An address earns a tier when activity over a completed TCP connection leaves its score at that
tier's floor. An entry is carried for a fixed time after the **last time it earned** its tier.
Later, weaker activity neither takes it out early nor extends it; only earning the tier again
does. UDP traffic naming the address changes nothing, since its source can be forged.

| Tier | Raw score | Confidence | Carried for |
|---|---|---|---|
| `tiers/aggressive` | ≥ 90 | ≥ 0.95 | 24 hours after it last earned the tier |
| `tiers/standard` | ≥ 75 | ≥ 0.70 | 48 hours after it last earned the tier |

The two files never list the same address. One that earned both stays in `aggressive` for its
24 hours and is then carried in `standard` for what is left of its 48.

Use `standard` unless you have a specific reason not to. `aggressive` is a narrower, higher-
confidence subset - appropriate for automated blocking on systems where a false positive is
cheap to recover from.

Each entry's `valid_from` / `valid_until` are anchored on the last time it earned its place, not on
the build time, so an entry's stated expiry is real: it is not renewed by later builds and it
leaves the file when the window lapses.

## Retention feeds

The two tiers answer "block this right now". The retention feeds answer "has this address been
active lately", which is usually the more useful question when building a long-horizon firewall
list.

| File | Contains |
|---|---|
| `retention/all-24h.*` | every tiered address that earned its tier, and every volume listing that made a TCP connection, in the last 24 hours |
| `retention/all-7d.*` | last 7 days |
| `retention/all-30d.*` | last 30 days |
| `retention/all-60d.*` | last 60 days |
| `retention/all-90d.*` | last 90 days |

These ignore tier and **nest**: `all-90d` is a superset of `all-30d`, which is a superset of
`all-7d`. Pick exactly one; there is never a reason to merge two. They include the volume
listings described under "What makes an entry"; the tier files do not. A volume listing is
carried from its last completed TCP connection; UDP traffic does not renew it.

## Formats

Every feed ships in all nine formats, under `tiers/` (aggressive, standard) or `retention/` (all-*).
Substitute `tiers/standard`, `retention/all-30d`, or any other feed path for `tiers/aggressive` below.

| File | Use with | Notes |
|---|---|---|
| `aggressive.txt` | anything | One IP per line, `#` comments |
| `aggressive.cidr` | anything | Host routes (`/32`, `/128`) |
| `aggressive.json` | APIs, tooling | Structured, includes per-entry metadata |
| `aggressive.csv` | spreadsheets | Header row, then one entry per line |
| `aggressive.ipset` | Linux ipset | Sets `propolis_aggressive_v4` and `propolis_aggressive_v6`; apply with `ipset -exist restore` |
| `aggressive.nft` | nftables | Sets `propolis_aggressive_v4` and `propolis_aggressive_v6` in table `inet propolis`; apply with `nft -f` |
| `aggressive.pf` | OpenBSD/FreeBSD pf | Table file, both address families |
| `aggressive.alias` | pfSense / OPNsense | URL Table alias source, both address families |
| `aggressive.rpz` | BIND, Unbound (RPZ) | A complete zone of `rpz-ip` triggers, both address families |

Every firewall file can be applied again and again: applying a newer copy leaves the set holding
exactly what that copy lists, so an address that has left the feed leaves your firewall too. An
empty feed is a valid file that empties the set. IPv4 and IPv6 addresses are kept in separate sets
where the tool requires it. In every format except `.json` and `.csv`, an IPv4-mapped IPv6
address (`::ffff:a.b.c.d`) is listed as the IPv4 address it is (`a.b.c.d`, and `a.b.c.d/32` in
`.cidr`), once even if the plain form is listed too. `.json` and `.csv` keep each entry under the
address it was recorded with.

`manifest.json` carries the build timestamp, per-feed entry counts, SHA-256 digests, and validity
windows. A count is the number of entries, which is the number of `.json` and `.csv` rows; `.txt`
can state one fewer for an address recorded in both forms, since it lists that address once.

### Per-entry fields

The `.json` and `.csv` formats carry, per address: `first_seen` (its first sighting of any kind),
`last_seen` (the hour the address last earned its place in that file, which is also its
`valid_from`), `events` (how many events over completed TCP connections back it), `categories`
(how many distinct sensor classes saw it), and `signals` - the distinct activity types it
triggered over connections it completed:

```
ssh_brute_force        honeypot_command_exec    honeypot_malware_upload
honeypot_file_download honeypot_login_attempt   port_scan
catchall_probe         waf_sqli_xss             ...
```

`signals` is what makes an entry actionable: it lets you keep the addresses that got as far as
uploading malware and drop the ones that only knocked on a port. In CSV it is the last column,
semicolon-separated. No score or confidence value is published, in either format.

### pfSense / OPNsense

Firewall → Aliases → URLs. Point a URL Table alias at:

```
https://raw.githubusercontent.com/brandontroidl/blocklist/main/tiers/aggressive.alias
```

Set the refresh frequency to 1 day. The alias updates itself.

### nftables

The file owns two named sets in the table `inet propolis` and nothing else. Applying it is one
transaction: both sets go from their old contents to the new ones at once.

```bash
# On a timer: fetch and apply. Safe to repeat; removed entries are removed.
curl -sO https://raw.githubusercontent.com/brandontroidl/blocklist/main/tiers/aggressive.nft
nft -f aggressive.nft

# Once: add your own chain and rules to the same table (a rule can only use a set in its table).
nft add chain inet propolis input '{ type filter hook input priority -5; policy accept; }'
nft add rule inet propolis input ip saddr @propolis_aggressive_v4 drop
nft add rule inet propolis input ip6 saddr @propolis_aggressive_v6 drop
```

Apply the file once before adding the rules, so the sets exist. Your chain and rules stay in place
across refreshes.

### ipset + iptables

Each family has its own set. The file fills a scratch set and swaps it in, so the live set is never
half loaded and rules that use it keep working during a refresh.

```bash
# On a timer: fetch and apply. -exist is required; without it the second run fails.
curl -sO https://raw.githubusercontent.com/brandontroidl/blocklist/main/tiers/aggressive.ipset
ipset -exist restore < aggressive.ipset

# Once:
iptables  -I INPUT -m set --match-set propolis_aggressive_v4 src -j DROP
ip6tables -I INPUT -m set --match-set propolis_aggressive_v6 src -j DROP
```

### pf

```
table <propolis> persist file "/etc/pf/aggressive.pf"
block in quick from <propolis>
```

After fetching a newer copy, replace the table's contents (this also removes what the file no
longer lists):

```bash
pfctl -t propolis -T replace -f /etc/pf/aggressive.pf
```

### RPZ (BIND, Unbound)

The file is a complete response policy zone. Each listed address is an `rpz-ip` trigger answered
NXDOMAIN: the resolver will not hand its clients an answer that points at a listed address. It does
not stop a listed address from querying your resolver.

```
// named.conf
zone "rpz.propolis" { type primary; file "/etc/bind/aggressive.rpz"; };
options { response-policy { zone "rpz.propolis"; }; };
```

After fetching a newer copy, `rndc reload rpz.propolis`. The zone's serial is the build hour.
Builds run more often than hourly (every 15 minutes by default), so two copies with different
contents can carry the same serial: reload the zone from the file, as above. A secondary, or
anything else that decides by serial alone, follows only at the next hour. The serial is not
made finer because that would publish when within the hour each build ran.

### Changed in this layout

If you used an earlier copy of these files:

- **nftables**: the file used to define a variable, `$propolis_aggressive`. It now maintains the
  named sets above. Replace `include` and `$propolis_aggressive` with the commands in the nftables
  section. Do it before the host next loads its configuration from nothing (at boot): a
  configuration that still includes the file and uses `$propolis_aggressive` then fails to load,
  which leaves the host with no ruleset. (A reload of a running ruleset fails as a whole and
  leaves the running rules in place.)
- **ipset**: the set `propolis_aggressive` is now `propolis_aggressive_v4`, with
  `propolis_aggressive_v6` beside it. Point your iptables rule at the new name, add the ip6tables
  rule, load with `-exist`, and destroy the old set once (`ipset destroy propolis_aggressive`).
  If you do nothing, the old set stops being updated and keeps blocking the entries it last held
  until you point your rule at the new sets and destroy it.
- **RPZ**: the earlier file had no SOA or NS record and its trigger names lacked the prefix
  length, so resolvers did not load it. The current file needs no editing.
- **hosts**: `aggressive.hosts` is no longer published. A hosts file maps names to addresses and
  cannot block traffic to or from an address, so that file blocked nothing. Use one of the
  firewall formats.

## Scoring

Scores are not cumulative counters. They decay.

- **Half-life: 6 hours.** A score of 100 decays to 50 after six hours of silence, 25 after twelve.
- **Deduplication: 60 seconds.** Repeat sightings of the same signal from the same IP inside
  one minute are recorded but add no weight, so a single burst cannot inflate a score.
- **Multi-vantage bonus.** An IP seen across multiple WAN addresses scores higher: +15% per
  additional vantage, capped at +60%. Scores are capped at 100 regardless.

Only activity over a completed TCP connection adds to a score; UDP traffic is recorded but adds
nothing, since its source address can be forged.

Decay decides whether an address **qualifies** and which tier it lands in, both evaluated at its
qualifying activity. It does not decide how long the entry is then carried - that is the fixed
window in the tables above, measured from the last time the address earned its place. An IP that
stops attacking still falls out of the list on its own; it does so on a stated schedule rather than
by sliding continuously between files.

The practical effect: presence in this list means *recently and repeatedly* hostile, not
"was hostile once, months ago."

## Never included

Filtered unconditionally, regardless of observed behavior:

- RFC 1918 private space (`10/8`, `172.16/12`, `192.168/16`)
- RFC 5737 documentation ranges (`192.0.2/24`, `198.51.100/24`, `203.0.113/24`)
- Loopback, link-local, multicast, limited broadcast
- IPv6 equivalents: `::1/128`, `fe80::/10`, `fc00::/7`, `ff00::/8`, `2001:db8::/32`
- Any operator-configured allowlist or explicit delist entry

The filter runs at build time and again at publish time, independently.

## Caveats

Read these before automating anything against this list.

- **One sensor.** This is a single node, not a distributed sensor network. Coverage is narrow.
  Absence from this list means nothing.
- **Shared and dynamic addressing.** An IP can be reassigned, or NAT many users. Blocking one
  may affect people unrelated to the attacker. The decay window limits but does not eliminate
  this.
- **No warranty.** Provided as-is. You are responsible for what you block. Test against your
  own traffic before enforcing anything in production.
- **Not a reputation service.** These are observations from one honeypot, not a judgment about
  any network or operator.

Found a false positive? Open an issue with the IP and I will delist it.
